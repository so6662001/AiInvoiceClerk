# 02 — 业务流程设计

## 1. 全局业务流程总览

```
客户登录 → 选择单据 → 校验开票资格 → 自动带出抬头 → 打款抬头校验
    → 提交开票申请 → 抬头与提货抬头比对 → [不一致则补签合同]
    → 开票运算引擎 → 进项库存匹配 → 税负/毛利调控
    → [库存充足] → 自动开票 → 调用诺诺网 → 发票回写 → 客户下载PDF
    → [库存不足] → 进入待开票队列 → 人工介入
    → [人工多开调整] → 人工审核通道 → 调整后重新提交
```

### 2.2 开票抬头自动带出与校验规则

开票抬头的自动带出是本系统最复杂的业务逻辑之一，需要处理多种打款场景和**多提货客户归一抬头**的特殊场景。

#### 2.2.0 多提货客户归一开票抬头场景

钢贸行业存在一种常见场景：多个提货客户（不同子公司、项目部、门店等）的提货单需要合并开票到同一个开票抬头。

**典型业务场景**

```
场景举例：
  某集团有 3 个子公司/项目部在我方分别提货：

  提货客户A（上海分公司）  → 提货单 DO001 ¥200,000
  提货客户B（杭州分公司）  → 提货单 DO002 ¥150,000
  提货客户C（南京项目部）  → 提货单 DO003 ¥180,000

  集团要求统一开票到：XX集团有限公司（母公司抬头）
  合计开票：¥530,000 一张发票

  类似场景：
  ├─ 集团与子公司：母公司统一采购，子公司分别提货
  ├─ 总包与分包：总包单位下单付款，多个分包商分别提货
  ├─ 贸易商与终端：贸易商下单，直发多个终端客户
  └─ 关联方代提：同一实控人下的多家公司互相代提货
```

**客户归集关系配置**

```

**多提货客户归一开票流程**

```
操作者（通常为归集组主客户的管理员）登录
  │
  ├─ Step 1: 进入开票申请，系统展示归集组内所有成员的可开票单据
  │   ├─ 按成员客户分组显示
  │   ├─ 可跨客户勾选单据
  │   └─ 显示每个成员的付款/授信状态
  │
  ├─ Step 2: 勾选多个成员客户的提货单
  │   例：勾选客户A的 DO001 + 客户B的 DO002 + 客户C的 DO003
  │
  ├─ Step 3: 系统校验
  │   │
  │   ├─ 3a: 各成员的开票资格分别校验
  │   │   ├─ 客户A（先款后票）→ 检查 A 的付款 ≥ DO001 金额
  │   │   ├─ 客户B（先票后款）→ 检查 B 的授信额度 ≥ DO002 金额
  │   │   └─ 客户C（先款后票）→ 检查 C 的付款 ≥ DO003 金额
  │   │   ★ 各成员独立校验，互不影响
  │   │
  │   ├─ 3b: 付款抬头校验（针对各成员独立进行）
  │   │   ├─ 各成员的对公付款只需在该成员内一致即可
  │   │   ├─ 不要求跨成员的付款抬头一致
  │   │   │  （因为各子公司本来就是不同法人打款）
  │   │   └─ 对私付款仍按原规则处理
  │   │
  │   └─ 3c: 开票抬头自动设定
  │       → 强制使用归集组主客户的抬头（XX集团有限公司）
  │       → 不允许切换到其他抬头
  │
  ├─ Step 4: 提货抬头一致性校验
  │   │
  │   ├─ 逐一检查每张提货单的 delivery_company 是否与开票抬头一致
  │   │   ├─ DO001 提货方"XX集团上海分公司" ≠ "XX集团有限公司" → 不一致
  │   │   ├─ DO002 提货方"XX集团杭州分公司" ≠ "XX集团有限公司" → 不一致
  │   │   └─ DO003 提货方"XX南京项目部"     ≠ "XX集团有限公司" → 不一致
  │   │
  │   ├─ 检查是否有有效的框架补充协议覆盖这些成员
  │   │   ├─ 有框架协议且未过期 → 免补签，继续 ✅
  │   │   ├─ 有免补签配置 → 继续 ✅
  │   │   └─ 无协议 → 触发补签流程
  │   │
  │   └─ 合同补签：
  │       生成的补充协议中列明所有涉及的提货方和单据清单
  │       签署方为开票方（XX集团）与我方
  │
  ├─ Step 5: 进入开票运算引擎（与常规流程相同）
  │
  └─ Step 6: 开票完成后
      ├─ 发票归属主客户（XX集团），主客户可查看/下载
      ├─ 各成员客户在"我的单据"中看到对应提货单已开票
      ├─ 开票申请单记录涉及的所有客户ID
      └─ 审计日志记录归集开票详情
```

#### 2.2.1 付款类型识别

| 付款类型 | 识别方式 | 说明 |
|---------|---------|------|
| 对公付款 | 付款方为企业对公账户 | 必须与开票抬头一致 |
| 对私付款 | 付款方为个人账户 | 可灵活开票，允许合并 |
| 第三方付款 | 付款方与购买方不是同一主体 | 需额外声明/授权 |

#### 2.2.2 抬头带出规则（决策树）

 │   │
 │   ├─ 有付款记录

 │   │   ├─ 全部为对公付款？
 │   │   │   │
 │   │   │   ├─ 是 → 检查所有付款方名称是否一致
 │   │   │   │       │
 │   │   │   │       ├─ 一致 → 自动带出该企业名称作为开票抬头 ✅
 │   │   │   │       │
 │   │   │   │       └─ 不一致 → ❌ 提示"存在多个对公打款主体，不可合并开票"
 │   │   │   │                   要求客户拆分单据分别开票
 │   │   │   │
 │   │   │   └─ 否（含对私付款）

 │   │   │       │   │         │         允许合并开票 ✅
 │   │   │       │   │         │
 │   │   │       │   │         └─ 不一致 → ❌ 提示拆分
 │   │   │       │   │

 │   │   │       │       → 使用客户档案中的默认开票抬头
 │   │   │       │       → 所有对私付款标记为"第三方付款"
 │   │   │       │       → 允许合并开票 ✅
 │   │   │       │
 │   │   │       └─ [第三方付款特殊处理]
 │   │   │           → 系统记录第三方付款声明

 │   │   │           → 开票抬头使用客户指定的抬头
 │   │   │
 │   │   └─ 无付款记录（先票后款客户）
 │   │       → 使用客户档案中的默认开票抬头 ✅
 │   │
 │   └─ [最终] 抬头信息展示给客户确认
 │
 └─ 结束
```

#### 2.2.3 第三方付款开票处理

```
第三方付款识别
  │
  ├─ 付款账户名称 ≠ 客户档案中任何关联企业名称
  │   → 标记为"疑似第三方付款"
  │
  ├─ 系统弹出提示：
  │   "检测到付款方 [XXX] 与您的开票抬头 [YYY] 不一致，
  │    请确认是否为第三方代付款？"
  │
  ├─ 客户确认 → 要求上传《第三方付款授权书》
  │   ├─ 模板由系统提供下载
  │   ├─ 需包含：委托方、受托方、付款金额、关联单据号
  │   └─ 上传后由系统自动 OCR 识别关键字段并校验
  │
  └─ 授权书审核通过 → 允许开票
     授权书审核不通过 → 人工审核队列
```

### 2.3 客户开票策略

#### 2.3.1 先款后票 (Payment Before Invoice)

```
单据创建 → 客户付款 → 付款确认到账 → 客户申请开票
                                        │
                                        ├─ 系统自动核对：
                                        │   已到账金额 ≥ 申请开票金额
                                        │
                                        ├─ 满足 → 允许开票
                                        └─ 不满足 → 提示"付款金额不足，
                                                    请补足差额后再申请"
```

#### 2.3.2 先票后款 (Invoice Before Payment)

```
单据创建 → 客户申请开票 → 系统检查授信额度
                          │
                          ├─ 授信额度充足 → 允许开票
                          │   扣减可用授信 = 当前可用授信 - 开票金额
                          │
                          └─ 授信额度不足 → 提示"可开票额度不足，
                                            请联系客户经理"
```

#### 2.3.3 策略配置

客户开票策略在客户档案中配置，支持以下维度：

| 配置项 | 说明 | 可选值 |
|--------|------|--------|
| invoice_policy | 开票策略 | PAYMENT_FIRST / INVOICE_FIRST |
| credit_limit | 授信额度 | 数值（仅 INVOICE_FIRST 有效） |
| allow_partial_invoice | 是否允许部分开票 | true / false |
| allow_merge_invoice | 是否允许合并开票 | true / false |
| match_strategy | 进项匹配策略 | EXACT_MATCH（大客户）/ FLEXIBLE（经销商） |
| price_adjustment | 价格调整方式 | ADJUST_WEIGHT / ADJUST_PRICE / NONE |

### 2.4 开票抬头与提货抬头一致性校验 + 合同补签流程

```
开票抬头 vs 提货抬头比对
  │
  ├─ 一致（所有单据提货方 = 开票抬头）→ 直接进入开票运算 ✅
  │
  ├─ 不一致（含多提货客户归一开票的情况）
  │   │
  │   ├─ 是否属于归集开票组？
  │   │   │
  │   │   ├─ 是 → 检查是否存在有效的框架补充协议
  │   │   │       │
  │   │   │       ├─ 有框架协议 → 校验协议覆盖范围
  │   │   │       │   ├─ 所有提货方均在协议范围内 → 免补签 ✅
  │   │   │       │   └─ 部分提货方不在范围内 → 仅对未覆盖的部分补签
  │   │   │       │
  │   │   │       ├─ 有免补签配置 → 跳过补签 ✅
  │   │   │       │
  │   │   │       └─ 无协议 → 触发补签流程
  │   │   │           补充协议中列明所有涉及的提货方及单据清单
  │   │   │
  │   │   └─ 否 → 常规不一致补签流程
  │   │
  │   └─ 触发合同补签流程（详见下方）
  │
  └─ 触发合同补签流程
      │
      ├─ 系统自动生成补充协议
      │   │
      │   ├─ 基于合同模板填充：
      │   │   ├─ 原提货方信息（可能有多个提货方）
      │   │   ├─ 新开票方信息
      │   │   ├─ 关联单据明细（按提货方分组列示）
      │   │   └─ 变更原因说明（归集开票 / 抬头变更 等）
      │   │
      │   └─ 生成合同 PDF 预览
      │
      ├─ 签署方式选择
      │   │
      │   ├─ 方式一：在线电子签 (推荐)
      │   │   ├─ 调用电子签章 SDK (e签宝/法大大)
      │   │   ├─ 发送签署链接到客户手机/邮箱
      │   │   ├─ 客户在线签名（支持手写签名/CA证书）
      │   │   ├─ 我方自动盖章（预设印章）
      │   │   └─ 双方签署完成 → 合同生效 → 继续开票流程
      │   │
      │   └─ 方式二：线下签署
      │       ├─ 客户下载合同 PDF
      │       ├─ 线下打印并手工盖章
      │       ├─ 扫描/拍照上传已签章合同
      │       ├─ 系统 OCR 识别印章
      │       ├─ 人工审核确认
      │       └─ 审核通过 → 合同生效 → 继续开票流程
      │
      └─ 合同状态流转
          DRAFT → PENDING_SIGN → SIGNING → SIGNED → EFFECTIVE
                                            │
                                     (线下方式多一步)
                                   UPLOADED → REVIEWING → EFFECTIVE
```

### 2.5 开票运算引擎

开票运算引擎是系统的核心计算模块，负责根据业务规则计算发票明细。

#### 2.5.1 客户分类与运算策略

```
┌─────────────────────────────────────────────────────────────┐
│                    开票运算引擎                               │
│                                                             │
│  输入：开票申请单（含单据明细、客户类型、开票抬头）              │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  Step 1: 识别客户类型                                │    │
│  │  ├─ 大客户 (VIP)                                    │    │
│  │  │   规则：怎么销售怎么开                             │    │
│  │  │   匹配策略：EXACT_MATCH                          │    │
│  │  │   含义：提货单上的品名、规格、单价、数量             │    │
│  │  │         必须与发票完全一致                         │    │
│  │  │                                                  │    │
│  │  ├─ 经销商 (DEALER)                                 │    │
│  │  │   规则：灵活调整                                  │    │
│  │  │   匹配策略：FLEXIBLE                             │    │
│  │  │   含义：在金额不超的前提下，根据进项库存、           │    │
│  │  │         税负率、毛利区间调整明细                    │    │
│  │  │                                                  │    │
│  │  └─ 用料企业 (END_USER)                             │    │
│  │      规则：灵活调整（同经销商）                        │    │
│  │      匹配策略：FLEXIBLE                             │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  Step 2: 运算规则执行                                │    │
│  │                                                     │    │
│  │  [大客户模式 - EXACT_MATCH]                          │    │
│  │  ├─ 提货单品名 → 发票品名                            │    │
│  │  ├─ 提货单规格 → 发票规格                            │    │
│  │  ├─ 提货单单价 → 发票单价                            │    │
│  │  ├─ 提货单数量 → 发票数量                            │    │
│  │  └─ 提货单金额 → 发票金额 (允许尾差 ±0.01)           │    │
│  │                                                     │    │
│  │  [灵活模式 - FLEXIBLE]                               │    │
│  │  ├─ 查询可用进项库存（品名+规格维度）                  │    │
│  │  ├─ 计算当前税务账税负率                              │    │
│  │  ├─ 确定目标毛利区间                                 │    │
│  │  ├─ 选择调整方式：                                   │    │
│  │  │   ├─ ADJUST_WEIGHT: 固定单价，调整重量             │    │
│  │  │   │   销项数量 = 销项金额 / 进项单价               │    │
│  │  │   │   (以价格为导向，调整重量使金额匹配)            │    │
│  │  │   │                                              │    │
│  │  │   └─ ADJUST_PRICE: 固定重量，调整单价              │    │
│  │  │       销项单价 = 销项金额 / 提货重量               │    │
│  │  │       (以重量为导向，调整单价使金额匹配)            │    │
│  │  │                                                  │    │
│  │  └─ 约束条件：                                      │    │
│  │      ├─ ❗ 发票金额 ≤ 单据金额（金额绝不允许多开）      │    │
│  │      ├─ 税负率在 [min_rate, max_rate] 区间内          │    │
│  │      └─ 毛利在 [min_margin, max_margin] 区间内       │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                             │
│  输出：发票明细行列表（品名、规格、单位、数量、单价、金额、税率）│
└─────────────────────────────────────────────────────────────┘
```

#### 2.5.2 税负率调控算法

```
输入参数：
  - current_tax_burden: 当前累计税负率
  - target_tax_range: 目标税负率区间 [min, max]
  - current_margin: 当前毛利率
  - target_margin_range: 目标毛利区间 [min, max]
  - available_inputs: 可用进项列表（含品名、规格、单价、库存量）
  - order_items: 提货单明细

算法步骤：
  1. 计算本次开票后的预测税负率
     predicted_tax = (累计销项税 + 本次销项税 - 累计进项税 - 本次可抵扣进项税)
                     / (累计销售额 + 本次销售额) × 100%

  2. 如果 predicted_tax 在 target_tax_range 内 → 直接使用
  3. 如果 predicted_tax < min → 需要减少进项抵扣
     → 减少匹配的进项数量或选择低税率进项
  4. 如果 predicted_tax > max → 需要增加进项抵扣
     → 增加匹配的进项数量或选择高税率进项

  5. 同时校验毛利约束
     margin = (销售额 - 进项成本) / 销售额 × 100%
     确保 margin 在 target_margin_range 内

  6. 如果无法同时满足税负率和毛利约束
     → 标记为需人工审核
     → 提供多组候选方案供选择
```

### 2.6 进项库存匹配

#### 2.6.1 匹配流程

```
开票运算结果（需要的品名、规格、数量）
  │
  ├─ Step 1: 精确匹配
  │   按 品名 + 规格型号 + 税率 查询进项库存
  │   │
  │   ├─ 库存充足 → 锁定库存 → 匹配成功 ✅
  │   │
  │   └─ 库存不足 → Step 2
  │
  ├─ Step 2: 模糊匹配（仅 FLEXIBLE 模式）
  │   按 品类大类 查询可替代进项
  │   │
  │   ├─ 找到替代项 → 重新计算明细 → 锁定库存 ✅
  │   │
  │   └─ 无替代项 → Step 3
  │
  └─ Step 3: 进入待开票队列
      │
      ├─ 记录缺口：品名、规格、缺口数量
      ├─ 发送通知给财务人员
      ├─ 状态变为 PENDING_INPUT（等待进项）
      └─ 后台定时任务：每30分钟扫描是否有新进项入库
          → 有新进项 → 自动触发重新匹配
          → 匹配成功 → 自动开票
```

#### 2.6.2 库存锁定机制

```
进项库存锁定采用"预锁定 + 确认"两阶段：

Phase 1 - 预锁定 (Try)
  ├─ 在 Redis 中创建锁定记录
  │   key: input_lock:{inputId}:{invoiceApplyId}
  │   value: 锁定数量
  │   TTL: 30 分钟（超时自动释放）
  ├─ 扣减 Redis 中的可用库存计数器
  └─ 发送锁定事件到 MQ

Phase 2 - 确认 (Confirm)
  ├─ 开票成功后，将 Redis 锁定记录持久化到 MySQL
  ├─ 更新进项库存表的已用数量
  └─ 删除 Redis 临时锁

Phase 3 - 回滚 (Cancel)
  ├─ 开票失败时，释放 Redis 锁定
  ├─ 恢复可用库存计数器
  └─ 发送释放事件到 MQ
```

### 2.7 人工介入通道

#### 2.7.1 自动转人工的触发条件

| 触发条件 | 说明 |
|---------|------|
| 进项库存不足 | 无法自动匹配足够的进项 |
| 税负率超出目标区间 | 无法同时满足税负率和毛利约束 |
| 第三方付款授权书审核 | 需人工确认授权书真实性 |
| 线下签署合同审核 | 需人工确认印章真实性 |
| 金额异常 | 单笔开票金额超过阈值 |
| 多开调整请求 | 客户或销售申请多开 |

#### 2.7.2 人工多开调整流程

```
多开调整（人工操作，非自动流程）
  │
  ├─ 触发入口：
  │   ├─ 运营/财务在后台管理界面发起
  │   └─ 系统自动开票后，支持人工追加调整
  │
  ├─ 操作步骤：
  │   1. 选择已开票/待开票的申请单
  │   2. 点击"人工调整"进入编辑模式
  │   3. 可修改内容：
  │      ├─ 增加/删除发票明细行
  │      ├─ 修改品名、规格、数量、单价
  │      ├─ 调整税率
  │      └─ 修改开票抬头
  │   4. 系统实时计算并展示：
  │      ├─ 调整后的金额汇总
  │      ├─ 预计税负率变化
  │      ├─ 进项匹配情况
  │      └─ 与原单据金额的差异
  │   5. 提交调整 → 主管审批
  │   6. 审批通过 → 执行开票/冲红重开
  │
  ├─ 审批流程：
  │   ├─ 差异金额 ≤ 1000 → 财务主管审批
  │   ├─ 差异金额 1000-10000 → 财务经理审批
  │   └─ 差异金额 > 10000 → 总经理审批
  │
  └─ 约束与风控：
      ├─ 记录完整操作日志（who/when/what/why）
      ├─ 多开金额上限控制
      ├─ 频次控制（同一客户月度多开次数限制）
      └─ 超限自动告警
```

### 2.9 异常处理与补偿

| 异常场景 | 处理策略 |
|---------|---------|
| 诺诺网接口超时 | 重试3次（指数退避），仍失败则进入人工队列 |
| 诺诺网返回开票失败 | 解析错误码，自动修正后重试或转人工 |
| 进项锁定后开票失败 | TCC Cancel 释放锁定库存 |
| 合同签署超时 | 48小时未签署自动提醒，72小时作废重新发起 |
| 重复提交开票申请 | 幂等校验（基于申请单号），拒绝重复请求 |
| 发票冲红/作废 | 支持红冲重开流程，释放已用进项 |
